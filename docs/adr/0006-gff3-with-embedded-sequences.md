# ADR 0006 — GFF3 with embedded sequences as a positional input

* Status: Accepted
* Date: 2026-09-11
* Deciders: petr
* Spec reference: §7.1 (inputs)
* Related: ADR 0005 (annotation overlay), which introduced the separate-file
  GFF3/BED loader this builds on.

## Context

ADR 0005 loads annotations from a file separate from the sequence: a FASTA for
the residues, a GFF3/BED for the intervals. The GFF3 specification allows a
single file to carry both — everything after a `##FASTA` directive line is a
FASTA section holding the sequences the features refer to. Tools in the
repeat-annotation chain (DANTE, DANTE_LTR, EDTA) emit such files, and keeping
the two halves together avoids the usual failure mode of a FASTA and a GFF3
drifting out of sync.

Before this change those files could not be used at all: passed as a sequence
they failed to parse as FASTA, and passed as an annotation the embedded
sequence lines were handed to `noodles-gff` as malformed records.

## Decision

1. **A positional sequence input may be a GFF3 with a `##FASTA` section.** The
   CLI (`dottir batch`, `dottir periodogram`) and the GUI (positional args,
   `File ▸ Open … sequence`) accept one such file for a self-comparison or two
   for a pairwise comparison. No FASTA is required.

2. **One loader for both forms.** `dottir_io::input::load_sequence_input` is the
   single entry point for a positional path and returns a `SeqInput`
   (sequence + optional annotations + raw bytes + kind). FASTA and
   GFF3-with-FASTA differ only inside it.

3. **Split before parse.** The `##FASTA` section is split off the raw bytes by
   `annotation::split_fasta_section` before either parser runs: features to
   `noodles-gff`, residues to the existing FASTA reader. `AnnotSet::load` uses
   the same split, so a GFF3-with-sequences loaded through the *separate-file*
   path also behaves (its features load; its sequences are ignored).

4. **Embedded features auto-bind in the GUI.** Opening such a file as the query
   binds its features as the query overlay (both axes in self-comparison mode).
   An explicit `--gff-query`/`--gff-subject` or a later `File ▸ Load GFF3/BED…`
   replaces them. Batch mode has no overlay, so it logs the feature count and
   drops them.

5. **Format detection by extension, with a sniff fallback.** `.gff`/`.gff3`
   (after stripping `.gz`) is GFF3; otherwise a leading `>` means FASTA and a
   `##gff-version` pragma in the first few lines means GFF3. A GFF3 with no
   `##FASTA` section is rejected as a *sequence* input with a message naming
   both fixes (append a section, or use `--gff-query`); it remains a valid
   annotation input.

## Consequences

* No new dependencies; no change to `dottir-core`, the pixelmap algorithm, or
  the pixelmap format version. A GFF3-sourced input and the equivalent FASTA
  produce byte-identical PNGs — asserted by
  `crates/dottir-cli/tests/gff3_input.rs`.
* Feature coordinates stay record-local, exactly as in ADR 0005; binding them
  to the concatenated buffer is unchanged.
* The sidecar hashes the file as given, so provenance points at the single
  GFF3 rather than a FASTA that no longer needs to exist.
* Corpus `tests/corpora/gff3_with_sequence/` (generated by
  `scripts/make_gff3_with_sequence_fixtures.py`) holds merged copies of the
  ADR 0005 fixtures plus a synthetic pair and a no-sequence negative control.

## Alternatives considered

1. **A `--gff-with-sequence` flag** instead of extension dispatch. Rejected:
   the file names its own format, and a flag would have to be repeated per
   axis for no gain.
2. **Rely on `noodles-gff` to stop at `##FASTA`.** Rejected: pre-splitting the
   bytes is a handful of lines, is independently unit-testable, and does not
   depend on parser behaviour across noodles releases.
3. **Accept a GFF3 without `##FASTA` and compute an empty plot.** Rejected: a
   silent empty dotplot is worse than an error naming the two ways forward.
